# Rebuilding source H5s from published split Zarr — 2026-11-27

**The published primary Zarr, derivative Zarr and summary JSON suffice to
rebuild the archived source H5 for every sampled recording in S0001, I0002,
I0003, I0004 and I0006 (25/25).** Every signal sample, annotation event,
feature time-series family and recording-summary row that the split format
carries matched the archived H5, and the converter's own source-to-export
verifier accepted every rebuilt H5 as the source of the published stores
(30/30). **I0007 cannot be rebuilt completely today: its derivative Zarr
stores are not published** (0 of 300 sampled subjects), so the rebuilt H5s
lack CAISR annotations and feature time series. Everything I0007 does publish
matched.

## Scope and reproducibility

- Read-only sources: `s3://bdsp-opendata-repository/PSG/bids/<cohort>/` for
  S0001, I0002, I0003, I0004, I0006 and I0007; for I0007 features, the
  producer run the derivative artifacts were built from
  (`s3://bdsp-staging/arpa-h-rest/sleep-features/runs/aws-i0007-fullprofile-v3-20261003/`).
- Sample: **5 subjects per cohort**, seed **20261127**, one seeded session per
  subject, 30 recordings. Every examined subject had a primary store and an
  archived source H5, so none was replaced. Cohort sizes: S0001 21,263,
  I0002 12,714, I0003 12,839, I0004 31,277, I0006 13,714 and I0007 22,033
  primary subjects.
- Code: `bdsp` 0.5.0 from this branch (`bdsp.zarr_to_h5`, `bdsp.h5_compare`),
  [`validation/h5_parity.py`](../h5_parity.py); converter verifier from an
  unmodified export of `bdsp-psg-conversion` `origin/main` at `c82da21`.
  Runtime: Python 3.12.13, Zarr 3.3.0, h5py 3.16.0, NumPy 2.4.3.
- [Method and command](../README.md#h5-parity-zarr-to-h5). Selections, per-recording
  results and object paths are kept privately in the ignored
  `validation/results/h5-parity-20261127/`. Downloads and rebuilt H5s were
  deleted after each recording. No cloud data were modified.

- **Signals.** All 1,024 source signals have identical rates, lengths and
  physical float32 samples, computed with the converter's calibration formula.
  83% were rebuilt as int16, 77% with the archived digital samples and 71% with
  the archived `phys_min/phys_max/dig_min/dig_max` attributes. The other int16
  signals use another calibration that reproduces the same values exactly. The
  remaining 17% are stored as float32 with an identity calibration: sparsely
  used or unusual ranges for which no short-decimal calibration reproduces
  every sample. Twelve PAP channels appended after conversion were also
  written, each naming its `*_desc-pap.h5`.
- **Annotations.** All 221 tables have identical codes and `event_map`s, and
  onsets and durations are bit-identical. `ends`, rebuilt as
  `starts + durations`, differs by up to 3.9 ms where a source table stored a
  slightly different float32 end (the converter accepts up to 10 ms).
- **Features.** Every published feature family matched its source group
  recursively: attributes, dtypes, shapes, masks, statuses and `information`
  fields (650/650). Summary columns matched for all 126,792 rows in the 24
  recordings with features, and all 22 summary arrays (the 1,024-D embedding),
  including their float32 dtype. Six sampled recordings (one S0001, one I0003,
  four I0004) have no computed features; their source H5s have none either.
- **Dates and identity.** Subject, session, duration, published age and sex
  matched for every recording. Root `meas_date` matched the source H5, using
  `h5_meas_date` where an I0006 summary JSON carries a corrected date.
- **Converter verifier.** With the rebuilt H5 standing in as the source,
  `verify_recording_zarr` reported no problems for every primary store (with
  appended channels left out, as the converter verifies those against their own
  file). It also reported no problems for each of the 25 published derivative stores,
  and `verify_features_json` none for each of the 30 summary JSONs.
- **Reader compatibility.** For one I0002 recording, `bdsp.read_h5`,
  `bdsp.open_h5` windows and `to_dataframe(resample_fs=100)` gave identical
  results for the rebuilt and the source H5. The synthetic tests cover the same
  calls.
- **Cost.** Median download 75 s, rebuild 43 s and comparison 15 s per
  recording (I0003's larger recordings: median rebuild 228 s). Rebuilt H5s were
  0.97–1.41× the source size, median 1.05.

## I0007: derivative Zarr not published

All five sampled I0007 sessions have a primary store and a summary JSON
(written 2026-11-09/10), but no `*_deriv-bdspsleepfeatures.zarr`. A separate
read-only listing of 300 seeded I0007 subjects found **no derivative Zarr for
any of them**: 299 have only the JSON and one has neither. For comparison, the
same listing found derivative Zarr for 95/100 S0001 subjects (5 have neither
artifact) and 100/100 in I0002, I0003, I0004 and I0006. The cohort's `CHANGES`
says I0007's "feature JSON and derivative zarr bundles" were rebuilt from the
feature H5 on 2026-11-09/10. These listings show the JSONs but not the Zarr
stores.

As a result, rebuilt I0007 H5s have expert annotations, signals and the full
recording summary (all rows and arrays matched the producer's feature H5), but
no CAISR annotations and none of the producer's temporal families (38 in three
sessions, 4 and 3 in the other two). This is missing input, not a writer failure. Publishing
I0007's derivative stores, e.g. with the converter's `--features-from`
reconversion, would close it.

## Not carried by the split format

These items occur in source H5s but are not stored in any split artifact, so
the rebuilt H5 lists them in `bdsp_h5_export` instead of inventing them. They
are not counted as failures:

| Item | Recordings |
| --- | --- |

| root `age_in_days`, `metadata_source`, `hypopnea_rule_source` | 30/30 |

| producer `package_name`/`package_version`, `provenance/json`, `recording/identity_json`, `features/research` | 19/19 with merged features |
| I0007 root `annotation_patch*` attributes | 5/5 |

## Limitations

- Five recordings per cohort test the method across every cohort's variants:
  PAP channels, corrected dates, separate feature H5s and recordings without
  features. They do not bound prevalence tightly: zero failures in the 25
  complete recordings gives an approximate 95% upper bound of 12% for this
  design.
- Parity covers what the split format carries. It does not restore the items
  above, and it does not show that other H5 consumers (e.g. Sleep YODA desktop)
  accept float32 signals or a missing `prefilter`.
- A different but exact int16 calibration changes the stored digital
  integers, not the physical values. Comparisons and the converter's verifier
  use physical values.
